Context Engineering

Context Engineering is the design and control of the information available to a model for a particular call. It includes the instructions, evidence, state, capability descriptions, examples, and prior interaction that the system delivers—and the decisions that determine what stays out, what changes form, and what can be recovered later.

The key phrase is for a particular call. A repository, memory store, tool catalog, and conversation may contain millions of useful tokens. The model does not act on that whole universe. It acts on the working set presented now, through the model interface, under a finite context window. Context Engineering is therefore less like filling a container and more like preparing the decision surface for the next step in a changing task.

This article develops that idea through one fictional shipping regression. The case is a teaching illustration, not a measured model run. It makes the design choices concrete while the source notes preserve the limits of the evidence behind the broader guidance.

The context engineering problem§

Imagine a coding agent asked to make checkout reject an unavailable shipping method before payment. The harness can search a repository containing more than 4,000 files. It gives the model a large packet: checkout code, old design notes, deployment logs, and several test reports. The model proposes a plausible change. The change is still wrong.

The packet omitted one controlling fact: the current shipping contract says that availability must be checked against the destination-specific service level returned by the quote service. The old design note describes a global availability flag. Both facts appear relevant, but only one governs current behavior. More volume did not compensate for the missing contract, and the presence of a stale explanation made the packet actively misleading.

The failure is not simply “the prompt was bad” or “the model needed more context.” It can be located more precisely:

  1. The call's decision was not stated narrowly enough to reveal which contract mattered.
  2. The source-selection process did not distinguish current authority from historical relevance.
  3. The delivered packet did not label the stale note as superseded.
  4. Nothing recorded the omission, so a reviewer could not reconstruct why the model never saw the controlling rule.

A corrected packet could be much smaller, but size alone is not the lesson. The corrected packet succeeds only if it contains enough current, authoritative material for this decision. In a less localized incident, a broader and well-organized packet might be the safer starting point. The goal is not minimum context. The goal is a sufficient, legible, and reviewable working set.

Working definition
Context Engineering is the deliberate construction and maintenance of the working set delivered to a model for a bounded decision, including its instructions, sources, organization, transformations, and lifecycle across calls.

The model call as the unit of design§

A useful way to reason about context is to start at the model boundary. For one call, ask what the harness can observe before and after the model is invoked. The harness can usually observe the material it intentionally supplied, the invocation settings it controlled, the response or tool call it received, and the state changes it recorded. It may not be able to observe provider-managed instructions, internal model processing, or hidden platform transformations.

This produces three distinct sets:

  • Candidate information is everything the system could potentially obtain: repository files, retrieved documents, memory records, tool descriptions, user messages, runtime state, and prior results.
  • Delivered context is the exact representation made visible through the model interface for this call, including order, labels, summaries, and any omitted portions.
  • Used information is whatever actually influenced the model's behavior. This last set is not directly observable merely because an item was present.

Context Engineering controls the path from candidates to delivery. It can make important information easier to use, but it does not guarantee that the model will use it correctly. That distinction prevents a common diagnostic mistake: finding a fact somewhere in the repository and assuming it was present, legible, and influential in the failed call.

The changing working set§

The working set changes as the task changes. A test run adds evidence. A tool call resolves one uncertainty and creates another. An implementation change makes an old file snapshot stale. A summary may replace exact history, while a large tool result may leave the active window but remain recoverable by an identifier.

The route to the current state matters too. Repository searches, discarded hypotheses, failed edits, and tool results can remain in a conversation after their immediate job is done. That accumulated route is the call's trajectory. Some of it is valuable: a rejected approach and the evidence against it can prevent repetition. Some of it is dangerous: an early guess can remain prominent even after better evidence arrives. Managing trajectory means turning what was learned into explicit current state, while keeping important history recoverable and clearly labeled.

For the shipping case, imagine that the first search found only the old global flag. A later trace finds the destination-specific contract. Replaying the entire search history gives the stale theory and the current rule similar visual weight. A better next-call packet states that the global-flag theory was rejected, identifies the contract that displaced it, and retains the earlier search under a reference in case a reviewer needs to reconstruct the change.

This produces four practical checks for a working set. They are design questions, not a validated scoring formula or a fixed priority order.

Four checks for the quality of a changing working set
Working-set check Concrete question
Correctness Is anything presented as current or controlling when it is false, stale, or merely assumed?
Sufficiency Does the call have the evidence, constraints, and capabilities needed for this decision?
Proportion Is the volume and detail justified by a current job, rather than by availability alone?
Trajectory Does the packet carry forward verified state and useful disagreement without letting obsolete exploration steer the next step?

Four design questions organize the rest of the article:

Four questions that organize a context decision
Design question What it makes explicit
What decision is this call making? The bounded outcome, success conditions, constraints, and current uncertainty.
What can the model actually see? The delivered instructions, evidence, state, capabilities, examples, and history—not merely what exists elsewhere.
What changed since the previous call? New evidence, resolved questions, stale material, state transitions, and anything removed or transformed.
How will the system judge the context change? The expected behavior, trace, failure, cost, or robustness difference and plausible competing explanations.

These questions form a dependency chain. The system must first clarify the decision, then locate candidate information, assemble a delivered packet, maintain it as the task evolves, and finally connect the context choices to observed outcomes.

Prompts and Instructions§

Prompts and instructions establish what the current call is trying to do and which directions control its behavior. Prompt engineering is therefore a local part of Context Engineering: it shapes one important class of context, while Context Engineering also covers evidence, state, capabilities, history, retrieval, assembly, and change across calls.

The most useful instruction usually identifies the decision at the right altitude. Too little direction leaves the model guessing about the outcome. Too much procedure can freeze an approach before the system has inspected the evidence. A strong instruction separates five concerns:

  • Outcome: what must be different when the step is complete.
  • Success conditions: what observation would show that the outcome holds.
  • Constraints: what must remain true, such as API compatibility or a safety boundary.
  • Known uncertainty: what is not yet established and may require retrieval or testing.
  • Expected response: what result, trace, or handoff the next system step needs.

Instruction altitude in the shipping case§

The following three instructions concern the same regression. Their differences show why both under-specification and premature procedure can fail.

Three instruction altitudes applied to the same shipping regression
Instruction What it supplies What it leaves unresolved Likely effect
“Improve checkout reliability.” A broad area of concern. The failing behavior, governing rule, compatibility constraints, and validation route. The model must invent the decision and may optimize the wrong behavior.
“Fix the shipping-availability regression shown by the failing test. Reject an unavailable shipping method before payment, preserve the public API and current tax behavior, run the focused test and checkout suite, and report anything you could not verify.” A bounded outcome, observable checks, constraints, and an uncertainty-reporting requirement. The implementation path, which should depend on current evidence. The model has room to investigate while remaining tied to the intended result.
“Open these five files in this order, change function A, add branch B, update fixture C, and inspect nothing else.” A complete procedure. Whether those files reflect the current contract or whether another dependency controls the behavior. The model may execute a stale theory efficiently and ignore contradictory evidence.

The middle instruction is not universally best because it is shorter or more abstract. It is useful here because the desired behavior and validation route are known while the correct implementation is not. If the task were a tightly regulated migration with an approved procedure, more explicit steps could be appropriate. If the failure were not yet localized, the instruction would need to preserve more exploratory latitude.

Instructions change with the decision§

One long task can contain several different decisions. An exploratory call may need to map a control path and report uncertainty without proposing a patch. A planning call may need to turn verified findings into a change sequence with explicit validation points. An implementation call may need to execute one approved slice and report the observed result. Reusing the same instruction for all three can mix discovery, commitment, and execution before the evidence is ready.

How the instruction and return artifact change with the immediate decision
Call's immediate job Instruction emphasis Useful returned artifact
Understand the regression Trace entry point, contract, control and data path, dependencies, and unresolved branches; do not assume the fix. Evidence-backed codebase map with exact sources and open questions.
Decide the change Use reviewed findings to name the intended edits, preserved constraints, and verification sequence. Reviewable plan whose assumptions point back to evidence.
Make a bounded change Implement the selected slice, run named checks, and update verified state rather than silently rewriting the plan. Diff, test results, deviations, and the next known decision.

This is an example of phase-specific context, not a mandatory three-stage workflow. A small, obvious correction may combine the decisions. A difficult investigation may need several research passes. G6 owns the workflow and its checkpoints; G2 asks whether each call's instruction and expected handoff match the decision it is actually making.

Precedence, provenance, and instruction-like text§

Real packets contain more than one source of direction: platform rules, system instructions, user requests, repository conventions, skill files, policy documents, and text returned by tools. These do not automatically have equal authority. The harness should preserve where a direction came from, which scope it governs, and how conflicts are handled.

Retrieved text can also contain imperative language. A stale design note that says “always use the global availability flag” is evidence about a former design, not a new controlling instruction. Treating every imperative sentence as an instruction collapses evidence and authority into one unsafe category. Security, permissions, and trust policy are owned primarily by G7; the local Context Engineering responsibility is to preserve their labels and precedence when constructing the current call.

Examples belong to the same design decision. A good example can demonstrate a format, boundary, or subtle distinction. A poor example can silently narrow the solution space or introduce facts that look authoritative. Examples should be included for a named reason, not because model-facing packets are assumed to be better when they contain demonstrations.

Once the call's decision and controlling directions are legible, the harness can determine what supporting information the call needs and where that information might come from.

Context Sources and Retrieval§

Context sources are the places from which candidate information can be obtained. They may include the current request, repository files, contracts, test output, databases, memory records, tool results, capability descriptions, run state, and prior messages. Source discovery identifies places that may hold an answer. Retrieval queries or fetches material from those places so it can be inspected. Selection decides which retrieved candidates have a job in the current packet. Delivery makes the chosen representation visible to the model. These operations can repeat in different orders as new evidence changes what the system needs.

Relevance is necessary but not sufficient. A source can discuss the right topic and still be stale, unofficial, incomplete, untrusted, or inappropriate for the current role. Selection normally considers several properties:

  • Decision relevance: which current requirement or uncertainty the item can resolve.
  • Authority: whether the item is allowed to govern the decision it appears to govern.
  • Freshness and version: whether it still describes the system under review.
  • Conflict: whether another credible source disagrees and the disagreement must remain visible.
  • Permissions and sensitivity: whether this call and role may receive the material.
  • Retrieval cost and recoverability: whether the item should be loaded now, summarized, indexed, or left available for later access.

From a source pool to a delivered packet§

The selection gates are questions, not a universal scoring formula or a single one-way filter. A current test result may be direct evidence of a failure but not authoritative about the intended product rule. A contract may govern behavior but say nothing about where the code implements it. Inspecting either item may expose a dependency that sends the harness back to discovery and retrieval. The useful packet often combines sources with different jobs while keeping those jobs and the iterative path visible.

The model often needs the relationship among them: where the request enters, which contract governs it, how data and control move, which dependency makes the final decision, and where the result can be observed.

Progressive disclosure§

Large systems rarely need every potentially useful item loaded in advance. Progressive disclosure gives the model a map, index, tool description, or compact summary first, then exposes full material when the evolving decision requires it. A repository tree can identify likely areas. A tool schema can explain how to request a quote-service trace. A memory index can show that a prior decision exists without placing the entire record in every call.

This strategy reduces irrelevant load only when the retrieval path is usable. The model needs enough information to know what is available, when to fetch it, and how to recognize failure. If an index omits the shipping contract, or a tool silently returns a stale version, deferred access merely hides the missing input. Material left outside the active window should therefore have an explicit recovery path and version semantics.

There is also a breadth tradeoff. In the localized shipping regression, the failing test and named contract justify a focused initial view. In an incident where the responsible subsystem is unknown, aggressively pruning to checkout code could blind the investigation. A broader but structured source map may be the correct first working set until evidence narrows the problem. Focus follows the state of knowledge; it is not a fixed packet-size target.

After sources are selected, they still have to be transformed into a coherent model-facing representation. That is the assembly problem.

Context Assembly and Delivery§

Context assembly turns selected material into the exact working set delivered to the model. Selection decides which information has a job. Assembly decides how that information appears: its type, label, order, excerpt, format, surrounding explanation, and relationship to other items.

A packet can contain all the right facts and still be hard to use. A current contract buried below a long stale discussion may receive less attention than its authority warrants. Two unlabeled passages can look mutually corroborating even when one is superseded. A summary can erase the uncertainty that should have prevented an irreversible action.

Anatomy of a call packet§

The layers are not mandatory fields for every call. They are a way to prevent different kinds of material from collapsing into undifferentiated prose. A short call may need only an instruction and one evidence item. A consequential decision may need explicit constraints, source versions, unresolved conflict, and a requested trace.

Match the representation to the decision§

Context is not only a choice of facts. It is also a choice of representation. A paragraph, sequence diagram, contract excerpt, call-stack tree, and file-tree diff can describe the same change at different levels. The useful form is the one that exposes the decision and its likely misunderstanding without forcing unsettled lower-level choices.

Applied to the shipping case, the decision views look like this:

Representations matched to five views of the shipping decision
Decision view Question being settled Representation that exposes it
User outcome What must checkout do differently? One outcome statement: an unavailable destination-specific service never reaches payment.
System interaction Which component supplies the governing fact? A short sequence from checkout to the quote service and back.
Interface contract What value controls the decision? The current request/response fields and availability rule.
Program shape Where should the rule be expressed in code? A call-stack tree, focused types or signatures, and a file-tree delta.
Verified change record What bounded change is ready to inform the next decision? A diff summary, observed behavior, focused check result, and preserved suite constraints.

These are not mandatory project phases. A localized fix may need only the contract and program shape. A product change with ambiguous behavior may need the outcome and system interaction reviewed first. Context Engineering owns which representation enters a particular call; it does not make the product, architecture, or workflow decision correct by itself. The change record is a model-facing representation of completed work, not the work sequence itself: G6 owns how a bounded slice is coordinated, and G8 owns how it is verified.

Intended, delivered, and observable context§

A prompt template is not proof of what the model received. Frameworks may add tool descriptions, system instructions, memory snippets, or transformed history. Providers may manage layers that the application cannot fully inspect. For review and evaluation, the system should distinguish:

  • the intended packet produced by its assembly policy;
  • the observable delivered packet recorded at the invocation boundary;
  • any managed or unknown layers that could not be captured; and
  • the model's response and resulting state change.

This article proposes a context manifest as one possible reconstruction record for that boundary. “Context receipt” is project shorthand, not an established industry term. Candidate fields include the call and decision, each item's type and source version, its delivered form and position, why it was selected, any transformation, and how the original can be recovered. The minimum practical schema remains an open research question.

Updating the next call§

After the first change at commit abc124, the focused shipping test passes. The required checkout suite now exposes a tax-rounding failure that passed in the recorded baseline run at abc123. That before/after difference does not prove the shipping change caused the failure, but the change cannot be accepted while its required suite is red. The next call therefore investigates the new failure while preserving the shipping contract and API constraint so that a tax fix does not undo the corrected behavior. It should not simply receive the entire previous packet plus the new log.

The preserved contract and API constraint maintain continuity. The new suite failure becomes current evidence. The long successful trace can leave the active packet while remaining recoverable by run identifier. The earlier implementation snapshot is either updated to the new commit or clearly marked as historical. This is context editing: preserve, add, update, remove, and retain-for-recovery are distinct actions.

Different roles may need different views of the same state. A worker making the code change may need the contract, focused implementation, and test command. A reviewer may need the diff, both test results, and the preserved constraints but not the entire exploration history. G6 owns which role acts and how work is coordinated; G2 owns the local question of what each selected role receives for its current decision.

A research note or plan may serve two audiences at once: it can align a human reviewer and become model context for the next phase. That does not mean both audiences need an identical rendering. The reviewer may need rationale, alternatives, and uncertainty at a glance. The model may need exact constraints, source excerpts, and a precise output contract. Both views should point to the same controlling decisions and recoverable evidence so that convenience does not produce two incompatible versions of the task.

The handoff also needs to show its uncertainty. Suppose a repository-research worker returns “availability is controlled by the global flag” without naming the files inspected or the unresolved quote-service branch. The coordinator receives a concise packet, but the isolation has hidden the exact place where the investigation stopped. A useful return packet includes its scope, evidence, conflicts, missing branches, confidence limits, and recovery references. A fresh context window prevents raw exploration history from spreading; it should not make incomplete research look settled.

Assembly and editing make the working set legible, but they do not remove the model interface's finite capacity. Long-running work requires explicit choices about what survives, what changes form, and what can be recovered.

Context Windows, Compaction, Compression, and Caching§

A context window is the finite amount of material the model interface can accept for a call, usually measured in tokens. The window is a hard boundary, not a target to fill. Long histories, repeated tool output, large documents, and expanding state compete for space with the instructions and current evidence that the next decision needs.

The terms below describe overlapping dimensions, not mutually exclusive boxes. Compression is an operation that makes a representation smaller. Compaction is a retention policy for an accumulated trajectory and often uses summarization or another form of compression. Clearing removes bodies from the active window. External state relocates selected information. Isolation gives another call a different working set. Caching reuses material or computation; it can reduce cost without changing model-visible context at all. It becomes a G2 concern when reuse changes what is delivered or whether the reused material is still valid.

Window-management mechanisms and the different problems they address
Mechanism What changes Appropriate use Main risk or adjacent owner
Compaction A retention policy replaces or reorganizes accumulated trajectory state, commonly using compression for part of the result. Continue a long task while retaining selected decisions, constraints, evidence, and open questions. Exact wording, numbers, uncertainty, and rejected alternatives can disappear; the policy and compression method must be judged separately.
Compression An operation makes a representation smaller through summarization, filtering, encoding, or structural reduction. Reduce size while preserving the information needed by a defined downstream decision; it may be used inside compaction or independently. “Shorter” can conceal irreversible semantic loss; the term covers methods with very different fidelity.
Tool-result clearing Old result bodies leave the active window while their call records or identifiers remain. Remove bulky output that can be fetched again reliably. Recovery may fail, return a different version, or cost too much.
External memory or state Selected information persists outside the active window and can be loaded later. Carry facts or decisions across calls or sessions. The wrong material can be saved, omitted, or reloaded stale; G3 owns the persistence mechanism.
Context-isolated worker A separate worker receives a bounded view instead of the coordinator's accumulated context. Separate a well-bounded decision from unrelated history. Handoff loss and orchestration effects; G6 owns worker control.
Caching A representation or computation is reused under a cache key; model-visible context may remain unchanged. Avoid repeating unchanged processing when validity conditions hold, or reuse a prior retrieval result deliberately. Staleness, invalidation, privacy, authority change, and confusion between reuse and correct selection; G9 owns production operation, while G2 examines delivered-content validity.

From temporary work traces to durable state§

Coding work produces a great deal of context that is useful while the work is happening but expensive or misleading to carry forever. File searches orient the investigation. Reads build a control-path model. Edit attempts expose constraints. Tests and builds create evidence. Large structured tool results may supply one decisive field. These traces are not worthless; they simply have a different lifecycle from the state the next decision needs.

Turning high-volume work traces into recoverable decision state
Accumulated work trace Durable state for the next call What remains recoverable
Search queries and dozens of candidate file hits The entry point, relevant dependency path, files actually inspected, and unresolved branches Exact query results and repository version
A rejected global-flag hypothesis The hypothesis, its rejected status, and the contract evidence that displaced it Original note and comparison record
Several failed edits The attempted approach, observed failure, and constraint learned from it Patch or commit identity and command output
A long test/build stream Exact failing assertion, environment, affected check, summary of passes, and run identity Complete immutable log
A large JSON response Decision-relevant fields, schema/version, omissions, and uncertainty Original payload under a stable identifier

The durable side should not contain only conclusions. It should preserve enough evidence and disagreement for another call—or a human reviewer—to decide whether those conclusions deserve to control downstream work.

Intentional compaction at a decision boundary§

Compaction need not wait until the window is nearly full. A meaningful boundary can be a useful trigger: exploration has produced a reviewable model, a plan has been approved for implementation, or a bounded slice has been verified. At such a boundary, the accumulated trajectory can be replaced with a reviewed checkpoint designed for the next decision.

The source's research → plan → implement workflow motivates this pattern, but it does not establish a universal trigger or sufficient checkpoint schema. This article proposes the following candidate fields for later testing:

  • the current goal and the decision now being made;
  • controlling requirements and constraints;
  • verified findings with exact source or run references;
  • rejected hypotheses and why they were rejected;
  • completed changes and the current repository or system state;
  • checks run, observed results, and unverified behavior;
  • unresolved questions, blockers, and confidence limits;
  • the next intended action; and
  • identifiers that recover omitted searches, logs, payloads, and prior versions.

This is more than summarizing the conversation. It transfers working and decision state from an exploratory trace to a smaller artifact for later calls; it does not transfer the authority of the underlying material. Contracts, evidence, and source records retain their own authority. The checkpoint carries their provenance, review status, uncertainty, and recovery references. As the structural-retrieval example showed, a concise checkpoint can still preserve a wrong dependency model. Review therefore remains necessary at the boundary.

No fixed token percentage determines the right moment. Task complexity, uncertainty, loss risk, recovery cost, and the presence of a real decision boundary all matter. The research → plan → implement sequence is one practitioner pattern that makes those boundaries visible, not a general law of Context Engineering.

Worked window decision: the long test log§

Suppose the checkout suite emits 500 lines. Most lines report passing tests. One block records the new tax-rounding failure, exact expected and observed values, environment, and test identity. Three different treatments serve different future needs:

  1. Keep exact in the active packet: retain the failing block and invocation metadata because the next call must diagnose those values.
  2. Summarize in the active packet: state that the remaining checkout suite passed, including the count and run identifier, because the full success stream is not needed for the current decision.
  3. Clear but keep recoverable: store the complete log under its immutable run identifier so a reviewer can inspect any omitted line later.

The defensible choice depends on a survival policy. Exact numeric evidence, current constraints, unresolved conflict, provenance, and recovery identifiers usually deserve stronger protection than repetitive progress output. But that is not a universal deletion rule. If intermittent timing behavior is under investigation, repeated timestamps that looked like noise may become the main evidence.

Fidelity and recoverability§

Every lossy transformation should make two questions explicit:

  • Which downstream decisions is the transformed representation intended to support?
  • If an omitted detail becomes important, can the system recover the exact original version?

Recoverability changes the risk of removal. Clearing an immutable log with a tested retrieval path is different from replacing it with an unaudited summary and discarding the source. Even a recoverable item may be practically lost if the next call does not know it exists, lacks permission to fetch it, or cannot afford the retrieval latency.

Caching requires a related validity judgment. A cached prompt prefix or retrieval result may be byte-identical while its authority has expired. A cache key should reflect the versions and conditions that make reuse valid, and the system needs an invalidation path when policies, permissions, tools, or source material change. Current G2 seed material identifies caching as important but does not yet support a general design recommendation.

With instructions, sources, assembly, and window management in place, the whole context lifecycle can now be seen as one connected control loop.

The complete context lifecycle§

The shipping case can be reconstructed as a ten-step sequence:

  1. Bound the decision. Fix the destination-specific availability regression without changing the public API or tax behavior.
  2. Derive context requirements. The call needs the observed failure, current availability rule, relevant implementation, validation route, and known constraints.
  3. Map known sources. The harness identifies contracts, test systems, repository areas, old notes, logs, and indexes that may hold needed material.
  4. Retrieve and trace. The harness fetches concrete versions, follows the behavior from checkout through the quote service, and marks unresolved branches instead of treating a list of files as understanding.
  5. Inspect and select. It applies authority, freshness, conflict, permission, and recovery questions and returns to retrieval when an inspected item exposes another need.
  6. Assemble and deliver. The packet labels the contract as controlling, the test as evidence, the old note as superseded history, and the code as the change surface.
  7. Observe the result. The response produces a change; focused and suite tests create new evidence.
  8. Checkpoint verified state. A reviewed handoff records the governing decision, rejected theory, current change, results, uncertainty, and recovery references without replaying all exploration.
  9. Edit for the next call. Resolved material leaves the active set, the new failure enters, snapshots update, and bulky logs remain recoverable.
  10. Evaluate and retain the trace. The system connects packet, invocation, result, and state change without claiming that presence proves causal use.

This lifecycle is recursive. Retrieval may reveal that the instruction is wrong. A test may change the decision. A permission boundary may remove a source and require escalation. Context Engineering is therefore a repeated control process around model calls, not a one-time prompt-building step.

How context failures appear§

Context failures are easier to diagnose when the context path is explicit. The first question below identifies a useful checkpoint, not a guaranteed cause; model capability, tool behavior, orchestration, security policy, and application code can produce similar symptoms.

Symptoms, context-path checkpoints, and competing explanations
Observed symptom First context-path checkpoint Competing explanation to keep open
Plausible work solves the wrong task. Were the outcome and success conditions explicit in the controlling instruction? The task itself may be ambiguous or internally inconsistent.
The response ignores a current fact. Was the fact retrieved, delivered, clearly labeled, and visibly current? The model may have received and misused it.
Relevant information was present but apparently unused. Was it buried, conflicting, weakly labeled, transformed, or delivered to the wrong role? The model may lack the reasoning capability the decision requires.
A later call loses a constraint. Did the delta, handoff, or compaction preserve it? Another system component may have overwritten the state.
A summary appears correct but later work fails. Which exact details survived and which were irreversibly lost? The failure may be unrelated to the summary.
A coherent plan expands a wrong assumption into many changes. Did its research input preserve sources, unresolved dependency branches, rejected alternatives, and review status? The domain model or requirement may itself be wrong.
A coordinator receives a confident but incomplete worker summary. Does the handoff expose inspection scope, evidence, uncertainty, missing branches, and recovery paths? The delegated investigation may have been poorly bounded or executed.
Two agents act from incompatible assumptions. Did their role-specific packets share current decisions and source versions? The workflow may lack a conflict-resolution protocol.
A result cannot be explained or compared. Can the intended and observable packet, transformations, invocation, and resulting state be reconstructed? Provider-managed layers may remain unavailable.

The table also shows why “add more context” is a weak default response. More material does not repair a missing governing source, an authority conflict, a stale summary, or a wrong-role delivery. Diagnosis should identify where the path broke before choosing a mechanism.

Evaluating a context change§

Evaluation asks whether a context choice improved behavior under stated conditions. G8 owns the general evaluation, verification, and observability method. G2's local responsibility is to make context variants and their traces specific enough to compare.

One successful focused packet does not establish that smaller packets are better. It may have removed misleading material, introduced the missing contract, improved organization, changed an instruction, or coincided with a different model outcome. A credible comparison keeps the task, model, tools, invocation conditions, and success criteria stable while varying the context policy deliberately.

Conditions that separate packet size from organization and sufficiency
Comparison condition What it helps distinguish
Credible current approach Establishes how the real system behaves before the change.
Broad, weakly organized packet Exposes the effects of carrying candidates without a reasoned structure or selection policy.
Broad, well-structured packet Tests whether organization—not deletion—accounts for the improvement.
Reasoned focused packet Tests the proposed decision-relevant selection and labeling.
Deliberately underspecified packet Reveals which success conditions fail when necessary information is absent.

Useful observations depend on the task but can include decision correctness, constraint violations, required tool use, recovery behavior, latency, cost, variance across repeated runs, and the ability to reconstruct failures. A context manifest connects those outcomes to what changed without turning correlation into proof of internal model use.

Immediate results and delayed consequences§

A context change can look successful at one horizon and remain uncertain at another. The focused shipping test answers an immediate behavior question. The checkout suite checks nearby regressions. Neither shows by itself whether the change made the code harder to modify months later. The practitioner source for this iteration emphasizes that mismatch: functional feedback can arrive in seconds, while architectural or maintainability costs may appear only after later changes. It also explicitly acknowledges that those delayed effects are difficult to benchmark and prove.

What context evaluation can and cannot establish at three time horizons
Observation horizon What can be observed What it cannot establish alone
Same call or focused run Instruction following, target behavior, tool use, exact failure, and recovery behavior Broad regression safety or durable design quality
Task completion Suite results, constraint preservation, review findings, implementation coherence, and rework before acceptance Ease of future change or long-term incident risk
Later codebase change Repeated defects, change surface, design drift, and effort needed to modify the area again That one earlier context packet caused the outcome; models, people, requirements, and code all changed in between

The longer the horizon, the more useful durable records become and the weaker simple causal attribution becomes. A context manifest can preserve the packet and decisions for later comparison, but it cannot make months of intervening changes disappear. G8 owns the evaluation design. G2's contribution is to make the tested context variant and its decision artifacts reconstructable at every horizon.

The current source set provides practitioner guidance, implementation examples, source-reported results, and useful negative cases, but not the independent controlled evidence needed for a general effectiveness claim. This article therefore presents a design model and evaluation questions, not a settled law that focus, phase handoffs, context isolation, or compression always improves quality.

Evidence status and open questions§

This v1.2 candidate retains the seven maintainer-approved seed reviews and adds one pinned practitioner repository as its sole new source lineage. It promotes no research finding. Four evidence classes remain separate:

  • Teaching illustration: the shipping regression, packet, run identifiers, and diagrams are invented to explain the model.
  • Project working model: the candidate-to-delivery lifecycle, design questions, manifest fields, and failure checkpoints organize the next research pass but are not approved findings.
  • Source-reported guidance: the seed cards preserve what vendor and practitioner sources recommend or report, with their limitations.
  • Established evidence: none has been promoted for G2.

The new source family also shows a useful refinement in emphasis. The earlier essay centers context management while already reporting the need for sustained human engagement and codebase expertise. The later essay adds stronger counterevidence: harness work is not sufficient by itself, a lights-off attempt failed, several layers of human review remain necessary, and the maintainability thesis lacks a good benchmark. This is one practitioner refining a view, not two independent sources agreeing.

The next research pass should pressure-test, extend, or replace this treatment. Important open questions include:

  • Which independent controlled studies isolate context composition from model, tool, orchestration, and prompt changes?
  • Under what task conditions does focus help, and when does broader structured context protect against premature narrowing?
  • How should authority, provenance, and security labels survive retrieval, summarization, caching, and handoff?
  • Which manifest fields are actually sufficient to reproduce and diagnose a model call across common runtimes?
  • How can semantic loss in compaction or compression be detected before it causes downstream failure?
  • Which fields must a phase-boundary checkpoint preserve, and how should an incorrect research artifact be detected before it becomes planning context?
  • When does a context-isolated worker improve focus, and when does its handoff merely hide incomplete retrieval or disagreement?
  • Which cache-validity and invalidation practices transfer across providers and harness architectures?
  • How should negative evidence—an unsuccessful retrieval, missing source, or failed recovery—be represented in the working set?
  • Which observations connect an immediate context improvement to delayed maintainability without overstating causality?
